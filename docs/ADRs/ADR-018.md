# ADR-018 — Fully agentic engineering

**Status:** Accepted · 2026-06-19

## Context

Plantry is built primarily by an automated, agent-driven workflow rather than by hand. At the time of this decision, that work used a Beads issue ledger, an implementation worker, a pre-flight critic gate, and a serial merge process. Those mechanics had existed in `AGENTS.md` and `.claude/skills` without a stated principle or rationale. As a result, decisions like "file the CI/CD work as beads for the pipeline to implement" (ADR-016) or "make CI an authoritative gate" only made sense in light of an intent a reader could not find.

Plantry is also intended as a **reference example of agentic engineering**. *How* the work is done is part of the project's purpose, not merely a means to the product — which is itself a reason to write the principle down rather than leave it implicit.

## Decision

**Fully agentic engineering is a foundational principle of this project**, peer to ADR-001 (DDD as the lens for the product). Concretely:

- **The implementation work that humans plan is carried out by the automated pipeline by default.** Humans own *intent* — product and architecture decisions, ADRs, issue specifications, and review/approval. The automation turns planned issues into implemented, gated, merged code. Beads is the seam: planned work lives as issues; the pipeline claims, implements, gates, and closes them.

- **It is a principle, not a guardrail.** Nothing prevents a human from editing code, and no such mechanism is wanted. When a task needs human judgement, or the automation is stuck, a human steps in — pragmatically, without ceremony. "A human wrote this by hand" is never a violation to be litigated; it is an allowed pragmatic choice.

- **Pragmatism over dogma, including about the process itself.** The pipeline is a means, not an end. When a process stops serving the work, we change the process rather than force the work through it. The principle is aspirational and mutable, judged by whether it produces good software well — not by adherence.

- **Quality is enforced by gates, not by trust.** Independent verification, review, QA, and required CI make "agents do the work" safe. The gates are non-negotiable and apply regardless of who — or what — authored a change. The current sequence is documented in the engineering workflow.

- **AI runs locally only.** Plantry is built on a Claude Code subscription, not an API plan, so every AI step — the Opus critic above all — runs through the local Claude Code CLI and **never in CI**. This is why the review gate is local and process-enforced while the correctness gate (CI) is server-side; see `docs/Engineering/agentic-workflow.md` ("The two gates").

## Consequences

- **The tooling is replaceable while the principle remains.** `AGENTS.md`, the current factory skills, Beads, and the CI gate (ADR-016) express this principle. Filing infrastructure work as Beads issues for the pipeline to implement is an application of the principle, not an exception.

- **Independent review and live QA carry the weight a human reviewer and tester would** in a conventional shop. They are first-class, improvable parts of the system, documented alongside the workflow rather than treated as fixed scaffolding.

- **The gate is author-agnostic by design.** Required CI applies to every PR regardless of author. This keeps the principle non-dogmatic without lowering quality; branch freshness and mergeability are verified before auto-merge.

- **Process is versioned like code.** Workflow changes are expected evolution, recorded in the engineering-workflow doc and ADRs rather than silent drift.

- **The project doubles as a worked example.** Process decisions are documented so the practice is legible to outside readers, not merely functional for us — reinforcing the OSS-bound posture (ADR-016).

## Note

The current mechanics live in `docs/Engineering/agentic-workflow.md` and the ADR-016 amendments. Earlier references in this ADR to the worker, critic, pre-flight, and orchestrator describe the historical implementation.

## Current operating model (2026-10-17)

The principle above remains in force. The live process is the serial one-ticket factory: each issue has one branch and PR, separate implementation, review, and QA roles, current-candidate evidence in Beads, and automatic merge only after every required gate passes. The issue closes after confirmed merge. See [the workflow](../Engineering/agentic-workflow.md).
